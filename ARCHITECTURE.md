# BananaWiki architecture

This document is the contract for anyone changing BananaWiki. Read it before
writing a feature; the rules at the end are checked in review.

## Layout

```
bananawiki/
  core/            infrastructure shared by the wiki and the hosting portal
    env.py         typed environment variables
    sqlite.py      connections, lifecycle guard, versioned migrations, Session helpers
    crypto.py      encrypted settings and token digests (1.4 compatible)
    passwords.py   Werkzeug password hashes
    timeutil.py    UTC timestamps ("YYYY-MM-DD HH:MM:SS")
    web.py         CSRF, CSP nonce, security headers, safe redirects
    assets.py      shared static serving and content-hash asset URLs
    static/        one design-system stylesheet for both applications
    ratelimit.py   in-memory and SQL-backed rate limiters
    i18n.py        JSON translation catalogues
    mail.py        outgoing email: SMTP (STARTTLS/SSL), Brevo, Resend, test outbox
    attention.py   when to email someone about waiting requests (modes, throttling state)
  wiki/            the wiki application
    app.py         create_app(): configuration, storage, features, request pipeline
    config.py      Config dataclass read from BW_* variables
    db.py          `db`: the request- or thread-bound database session
    auth.py        sessions, current user, access decorators, permission checks
    permissions.py permission catalogue, roles, category access
    accounts.py    account creation, passwords, renames, deletion
    settings.py    the site_settings row
    registry.py    Feature, NavItem, Job, events, template slots, scheduler
    attention.py   "needs your attention": approval queues per user, events for new items and decisions
    storage.py     uploaded files on disk
    markdown.py    Markdown -> sanitised HTML
    templating.py  template globals and filters
    i18n.py        request language and t()
    migrations/    schema versions (baseline_v3.sql + numbered Python upgrades)
    takeover.py    first start on a 1.4 installation
    templates/     base layout, macros, error page
    static/        wiki content CSS, core JS, bundled favicons
    translations/  core strings (en, it)
    features/      one package per feature (see below)
  hosting/         the hosting portal (multi-tenant wiki provisioning); runtime/ drives
                   tenant containers through the root runtime agent
  ops/             the `banana` lifecycle CLI (install, update, backup, restore) and
                   the runtime agent (see ops/RUNTIME_AGENT.md)
  desktop/         the portable desktop launcher
  sdk/             userbot client and the 1.4 plugin SDK compatibility layer
  cli.py           the `bananawiki` administration command
bananawiki_sdk/, bananawiki_userbot_sdk/   1.4 import names kept for plugins and scripts
banana, wsgi.py, gunicorn.conf.py, hosting/, scripts/tts_worker.py
                 entry points with 1.4 names: installed servers and the 1.4 updater run them
contrib/         optional extras (remote GPU text-to-speech server)
packaging/       desktop app build (PyInstaller)
deploy/          Caddy and systemd examples (generated by bananawiki.ops)
docs/            documentation; docs/1.4-review.md lists what 1.6 fixed
tests/           pytest suite (conftest.py documents the fixtures;
                 tests/fixtures/v1_instance is a real 1.4 instance for upgrade tests)
```

## Request pipeline

`app._install_request_pipeline` runs for every request, in this order:

1. Stateless views (`@auth.stateless`: health checks, `/source`) return immediately.
2. Global per-client rate limit (in memory).
3. Requests to `/api/` with `Authorization: Bearer` skip session handling;
   the API authenticates them itself and CSRF does not apply.
4. `auth.load_request_user()` resolves the session cookie into `g.user`.
5. Setup gate: until setup is done everything redirects to `/setup`.
6. Access: views are **private by default**. `@auth.public` views are open to
   everyone; `@auth.public_read` views are open to anonymous visitors while
   public mode is on. Everything else redirects anonymous visitors to sign-in.
7. Account state: suspended, pending or denied accounts only reach views
   marked `@auth.exempt("approval")`.
8. Maintenance mode: only administrators pass (views may be exempted).
9. Forced account steps (password change, onboarding).

CSRF is checked for every unsafe method except bearer API calls. Forms send
`csrf_token`; scripts send the `X-CSRF-Token` header (`BW.fetchJSON` does it).

## Database

SQLite in WAL mode, one file. Use the `db` object:

```python
from bananawiki.wiki.db import db

row = db.one("SELECT * FROM pages WHERE id = ?", (page_id,))      # dict or None
rows = db.all("SELECT ...", params)                                # list of dicts
n = db.scalar("SELECT COUNT(*) FROM ...", params, default=0)
ids = db.column("SELECT id FROM ...")
new_id = db.insert("table", {"col": value})
db.update("table", {"col": value}, "id = ?", (row_id,))
with db.transaction():            # BEGIN IMMEDIATE ... COMMIT; nests as savepoints
    ...
```

Connections are autocommit: a single statement commits on its own; anything
that must be atomic goes inside `db.transaction()`. Always use `?`
parameters. Identifiers passed to `insert`/`update` must be literals in your
code, never user input.

Timestamps are TEXT in UTC, shaped `YYYY-MM-DD HH:MM:SS`. Use
`core.timeutil.now_sql()`, `sql_in(hours=48)`, `parse()`, `is_past()`.
Display them with the `|datetime`, `|date` and `|time_ago` filters (site time
zone). Convert `datetime-local` form input with `templating.from_local_input`.

### Schema changes

The schema is versioned (`PRAGMA user_version`). BananaWiki 1.4 databases are
at version 3; version 4 is the 1.6 takeover migration, version 5 adds the
durable chat upload usage ledger, version 6 records who imposed a
suspension and version 7 counts read-aloud claims lost with their worker
(`tts_generations.attempts`). New schema changes need a numbered migration
registered in `migrations/__init__.py` so existing installations receive them.
Feature schema helpers must be idempotent (use `CREATE TABLE IF NOT EXISTS`
and `core.sqlite.add_columns`). The takeover still calls `upgrade_v4(conn)`;
later migrations call the relevant feature helper. Never change
`baseline_v3.sql`; it is the
1.4 schema. Existing tables and columns keep their names and meaning so an
upgrade needs no data rewrite.

## Features

A feature is a package `bananawiki/wiki/features/<id>/` whose `__init__.py`
defines `FEATURE`:

```python
from ...registry import Feature, NavItem, Job
from .routes import bp

FEATURE = Feature(
    id="kanban",                     # also the row id in `plugins` for toggle="plugin"
    name="feature.kanban.name",       # translation keys
    description="feature.kanban.description",
    toggle="plugin",                 # "always" | "plugin" | "setting" (+ setting="column")
    default_enabled=True,
    easy_wiki=False,                 # hidden when BW_EASY_WIKI=1
    blueprints=[bp],
    nav=[NavItem("kanban.nav", "kanban.index", icon="columns", area="apps",
                 visible=lambda user: ...)],
    jobs=[Job("kanban.prune", 3600, prune_events)],
    events={"page.deleted": [on_page_deleted]},
    slots={"page.below_content": render_panel},
    attention=[AttentionSource("kanban.requests", "kanban.attention.requests", "kanban.admin_requests",
                               count=lambda user: pending_requests() if auth.is_admin(user) else 0)],
)
```

* Build the blueprint with `registry.feature_blueprint(id, name, __name__,
  template_folder="templates", static_folder="static",
  static_url_path="/static/<id>")`; it answers 404 while the feature is off.
  Features that are always on use a plain `Blueprint`.
* Templates live in `features/<id>/templates/<id>/…` and extend `base.html`
  (or `base_minimal.html`). Static files live in `features/<id>/static/` and
  are linked with `asset_url('file.js', blueprint='<blueprint name>')`.
* Ordinary pages use the shared 1120px content frame. Article prose uses the
  800px reading measure inside it. Only spatial workspaces such as the page
  editor, Kanban board and canvas use `main--wide`; authentication screens
  and modal dialogs may be narrow. Use the shared form macros and button
  classes, and `section-stack` for settings sections rather than nested
  cards. Feature styles should not introduce arbitrary page width caps.
* Strings live in `features/<id>/translations/{en,it}.json`; both languages
  are required and must have the same keys. Keys under `js.` are shipped to
  the browser (`BW.t('key')` without the `js.` prefix).
* `registry.is_enabled(id)` is the only feature switch. Disabling a feature
  never deletes data and never rewrites its settings.

### Approval queues ("needs your attention")

Anything that waits for someone's decision is declared as an
`AttentionSource(id, label, endpoint, count, endpoint_args={}, oldest=None,
audience="admin"|"editor", order=100)` in `Feature.attention`:

* `count(user)` returns how many items **this user** may act on (0 for
  everyone else) with one cheap, indexed query; `oldest(user)` optionally
  returns the timestamp of the item waiting longest; `audience` is the lowest
  role that can ever act on the queue (the email job skips everyone below it).
* `bananawiki.wiki.attention` collects the queues of enabled features:
  `items(user)` (cached per request; the account menu's red dot and section,
  the admin dashboard, `/attention` and the banner after sign-in read it),
  `counts(user)`, `total(user)`, and `badge(source_id)` for a `NavItem.badge`
  that reuses the cached count.
* When a new item is stored, call `attention.created(source_id, object_id)`
  after the commit; when someone's own request is decided, call
  `attention.decided(user_id, source_id, "approved"|"denied", object_id=…,
  endpoint=…)`. The `attention` feature turns these events into notices and
  emails (`attention.notify` job; modes and throttling in
  `bananawiki.core.attention`). Emails contain counts and links, never content.

The hosting portal has the same model in `bananawiki.hosting.attention`
(no feature registry: the three queues are listed there, emails are sent by
the maintenance service).

### Events

Services emit events after their transaction commits with
`registry.emit(name, **payload)`. Handlers of disabled features are skipped;
a failing handler is logged, never raised.

| Event | Payload |
|---|---|
| `page.created` | `page`, `author_id` |
| `page.updated` | `page`, `previous`, `author_id` |
| `page.moved` | `page`, `previous_category_id`, `actor_id` |
| `page.renamed` | `page`, `old_slug` |
| `page.deleted` | `page`, `actor_id` |
| `page.restored` | `page`, `actor_id` |
| `category.created` / `category.deleted` | `category`, `actor_id` |
| `user.created` | `user` |
| `user.renamed` | `user`, `old_username`, `changed_by` |
| `user.name_released` | `user`, `username` (the former name), `released_by`, `reserved_for` (None: anyone may take the name; else the account that gave it up before, which keeps it) |
| `user.deleted` | `user`, `deleted_by` |
| `user.login` | `user` |
| `user.password_changed` | `user_id` |
| `user.role_changed` | `user`, `old_role`, `new_role`, `changed_by` |
| `user.suspended` | `user`, `until` (None: permanent), `actor_id` |
| `user.password_reset` | `user`, `actor_id` (an administrator replaced the password; revoke other credentials) |
| `assessment.completed` | `user_id`, `page_id`, `assessment_id`, `attempt_id`, `score`, `max_score` |
| `attention.created` | `source`, `object_id` (a new item in an approval queue) |
| `attention.decided` | `user_id`, `source`, `outcome` (`approved`/`denied`), `object_id`, `endpoint` |

### Template slots

Features add HTML to other features' pages through slots
(`{{ slot('name', **context) }}` in templates, `Feature.slots` to fill them).
Return `Markup` (or a string of already-escaped HTML); render with
`render_template` so autoescaping applies.

| Slot | Where | Context |
|---|---|---|
| `topbar.actions` | top bar | — |
| `sidebar.top`, `sidebar.navigation`, `sidebar.bottom` | sidebar | — |
| `page.banners` | above every page | — |
| `page.scripts` | end of `<body>` | — |
| `footer.links` | footer | — |
| `page.header_actions` | wiki page header | `page` |
| `page.above_content`, `page.below_content` | wiki page | `page` |
| `page.sidebar_panel` | wiki page side panel | `page` |
| `editor.below_form` | page editor | `page` (None when creating) |
| `auth.login.below_form` | sign-in page | `next_url` |
| `auth.account_status` | suspended/pending page | `state`, `user` |
| `auth.onboarding.fields` | onboarding form | — |
| `profile.sections` | user profile | `profile_user` |
| `account.settings_sections` | account settings | — |
| `admin.dashboard` | admin dashboard | — |

### Interceptors

Some features change what another feature's action does (deletion slowdown
turns "delete" into "schedule deletion"; page protection blocks edits).
`Feature.interceptors = {"point": handler}`; the owner of the action calls
`registry.intercept("point", **context)` and uses the first non-`None`
answer. Unlike events, interceptors run before the action and their errors
propagate. `registry.prepare("point", **context)` instead runs the
interceptors of the point of every built-in feature, switched off or not,
and of enabled external plugins, and ignores their answers: features use it
to keep their stored data intact. A failing interceptor is logged with its
feature's id and stops the action.

| Point | Called by | Context | Answer |
|---|---|---|---|
| `page.edit_blocked` | pages, before showing or saving the editor | `page`, `user` | translation key explaining why editing is blocked, or `None` |
| `page.edit_denied` | pages, when the user may view but not edit | `page`, `user` | a response (e.g. redirect to "propose an edit"), or `None` for 403 |
| `page.delete` | pages, before deleting | `page`, `user` | a response when the feature handled it (e.g. scheduled deletion), or `None` to delete now |
| `page.saved` | pages, after a successful save from the editor | `page`, `user` | ignored (use for releasing check-outs, clearing drafts) |
| `page.create_denied` | pages, when the user may not create in a category | `user`, `category_id` | a response, or `None` for 403 |
| `user.delete` | `accounts.delete` through `registry.prepare`, inside its transaction, just before the row goes | `user`, `deleted_by` | ignored (hand over rows the database would delete with the account, e.g. kanban tickets) |
| `page.render` | pages, when rendering a page body | `page` (with content) | `Markup` replacing the Markdown body (page builder pages), or `None` |

### Background jobs

`Job(name, interval_seconds, function)`. A scheduler thread in each worker
runs due jobs; a lease in `job_runs` guarantees one worker runs a job at a
time. Jobs of disabled features do not run. Jobs run inside an application
context with a database connection (`db` works). Operators can also run
`bananawiki jobs run` from cron.

### Shared services other features may use

* `features/pages/service.py` - page reads, visibility (`can_view`,
  `visible_filter`), create/update/delete/move/revert, history, search.
  **Every page write goes through it.**
* `features/pages/categories.py` - category tree and changes.
* `accounts.py` - create accounts, change passwords, rename, delete.
* `auth.py` - `current_user()`, `has_permission()`, `has_role()`,
  `is_admin()`, `can_read_category()`, `can_write_category()`,
  `revoke_sessions()`, decorators.
* `settings.py` - `load()`, `get()`, `update()`, `public_mode_active()`.
* `storage.py` - `save()`, `send()`, `resolve()`, `delete()`.
* `markdown.py` - `render()`, `highlight_code()`, `to_plain_text()`, `excerpt()`.
* `attention.py` - `created()`, `decided()`, `items()`, `badge()` (see above).
* `core/mail.py` - `send(settings, Message)`; features get the wiki's mail
  settings from `features/attention/service.mail_settings()` and must send
  from a job, never inside a request.

## Front end

* No inline scripts or event handlers: the CSP forbids them. A page that
  needs data passes it as `<script type="application/json" id="…">{{ data|json_script }}</script>`
  and a script file reads it. A truly inline `<script>` needs
  `nonce="{{ csp_nonce() }}"`.
* `static/js/bananawiki.js` provides `BW.fetchJSON`, `BW.t`, `BW.toast`,
  and declarative hooks (`data-confirm`, `data-dialog-open`, `data-copy`,
  `data-autosubmit`, `data-toggle-target`, `data-print`).
* Build user-supplied text into the DOM with `textContent`, never
  `innerHTML`.
* Use the design-system classes in `bananawiki/core/static/css/bananawiki.css`
  (`btn`, `card`, `field`, `form-section`, `table`, `alert`, `badge`, `tabs`,
  `menu`, …) and its colour and control tokens. Both applications serve this
  source at `/static/css/bananawiki.css`; do not copy it into an application.
  Feature CSS goes in the feature's static folder and defines feature layout.
* Settings use `form-section` inside `section-stack`. Reserve `card` for
  standalone surfaces; avoid styling a card and then cancelling its surface.
  Keep each component's base, state and responsive rules together.
* Pages must work at 360 px wide and with the keyboard alone.

## Rules

1. Every route checks authorisation explicitly (login is the default;
   roles and permissions are not). Object-level checks: the user may see or
   change *that* page/board/chat/file, not just "some" page.
2. Never trust client-supplied ids to belong to the user; look the object up
   and check ownership or visibility.
3. No `|safe` on anything built from user input or translations with
   parameters. Markdown goes through `markdown.render`.
4. Uploads go through `storage.save` (random names, size and type limits,
   metadata stripped from images) and downloads through `storage.send`.
5. State changes use POST (or PUT/PATCH/DELETE for JSON endpoints), never GET.
6. Keep 1.4 URLs working; redirect when a URL moves.
7. Every feature ships tests in `tests/features/` covering its
   permission checks, main flows and edge cases.
8. Strings are translated (en + it). No hard-coded user-facing English.
9. No new dependencies without a strong reason; nothing that needs a
   compiler at install time.
