# Review of BananaWiki 1.4

Before 1.6 was written, the 1.4 code base (commit `2d9ad2f`, the first public
release) was audited in four parts: core application and security, database
schema, features and plugin system, and deployment, operations and hosting.
This page collects everything the audits found wrong and says what 1.6 does
about each item. File and line references point into the 1.4 tree at that
commit.

Status words:

* **Fixed**: the problem cannot happen in 1.6.
* **Changed**: the behaviour was redesigned; the new behaviour is described.
* **Partly**: improved, with a remaining limitation that is stated.
* **Open**: not addressed; the reason is stated.

For the practical consequences of the changes (what behaves differently
after an upgrade), see [UPGRADING](../UPGRADING.md).

## 1. Security of the core application

### Critical

**C1. Approval of sign-ups was never enforced.** With `approval_required` on,
new accounts were stored as `pending` (`db/_users.py:150-151`), but nothing
read that value: `/login` (`routes/auth.py:246-376`), `/admin` sign-in
(`routes/admin_sessions.py:154-285`), `/session-conflict/force`
(`routes/auth.py:643-710`), `login_required` (`helpers/_auth.py:298-345`) and
the request guards (`app.py:1160-1190`) all let pending and denied accounts in.
The `/activation-pending` and `/activation-denied` pages
(`routes/auth.py:729-784`) were never reached. Reproduced: a pending account
signed in and read pages.
*Fixed.* Account state is part of the request pipeline: suspended, pending and
denied accounts reach only their status page (`auth.account_block` and the
`approval` gate in `bananawiki/wiki/app.py`), and bearer tokens of such
accounts get `403 account_blocked`.

**C2. Site import could overwrite `config.py`, the secret key and the live
database, i.e. run code.** `restore_system_files` (`routes/admin_migration.py:856`)
made `_import_site_migration_assets` (`:350-398`) write `instance/config.py` to
`BASE_DIR/config.py`, the key file and `DATABASE_PATH` with plain `open()`
while the app ran, with no managed-hosting gate; the replaced `config.py` ran
at the next restart, which the administrator could trigger. The upload was
also read fully into memory (`:686`).
*Fixed.* Import only ever writes the database and the data folders; code, the
secret key and anything else in the archive is ignored. The archive is
unpacked into a staging folder, checked (paths, sizes, links), its database
must pass an integrity check, carry BananaWiki's application id and an
upgradable schema, upgrade cleanly and contain a finished setup, an
administrator and a home page. Only then is the live database replaced with
SQLite's backup API (safe with open connections) in maintenance mode, after
the current site was copied to `<instance>/backups/pre-import-<time>/`; any
failure restores that copy. Imports are off under managed hosting
(`BW_ALLOW_SITE_IMPORT`). See `features/site_admin/migration.py`.

### High

**H1. The guided tour's role preview gave any user administrator views.**
`_tour_preview_user_for_request` (`helpers/_auth.py:175-197`) replaced the
user's role with the tour role for GET requests; any user could pick `admin`
(`routes/onboarding.py:73`, `:588-603`) and then read `/global-settings`,
`/admin/users` and restricted category titles.
*Fixed.* The tour is a set of static illustrations; choosing a role changes
the explanations shown, never what the account can see
(`features/auth/tour.py`).

**H2. A session cookie issued to a suspended user could not be revoked.**
Suspended sign-in, `/admin` sign-in and `/session-conflict/force`
(`routes/auth.py:278-291`, `routes/admin_sessions.py:226-233`,
`routes/auth.py:627-632`) set `session["user_id"]` without a server-side
session row; `app.py:1263-1269` accepted such cookies, so they survived
unsuspension, password reset, session revocation and mass logout. Root cause:
two parallel session systems.
*Fixed.* One session system: a request is signed in only when the cookie's
token matches an active `user_sessions` row of the same account
(`bananawiki/wiki/auth.py`). Cookies without a server session are cleared.
Suspension, password changes, resets and mass logout revoke the rows.

**H3. A successful sign-in reset the per-address failure counter.**
`_clear_login_attempts()` (`routes/auth.py:347`, `routes/admin_sessions.py:275`,
`routes/auth.py:705`) deleted all failures of the address, so an attacker with
any valid account could guess others' passwords without limit; there was no
per-account limit, the check was not atomic, and behind a proxy without
`BW_PROXY_MODE` everyone shared one bucket.
*Fixed.* Failures are counted per address (20) and per account name (8) in 15
minutes in the shared `rate_limit_hits` table; a success clears only its own
account's counter (`features/auth/signin.py`).

**H4. Most permissions were decorative.** `page.create`, `page.edit_all`,
`history.revert`, `history.view`, `page.edit_metadata`, `page.view_all`,
`category.view_all`, `draft.*`, `search.pages` and `search.users` were never
checked (`routes/wiki_editing.py:31-45, 236-320`, `routes/wiki_history.py:314-347`).
*Fixed.* Every key in the catalogue (`bananawiki/wiki/permissions.py`) is
enforced by the routes and API calls it names, and a permission of a
switched-off feature is never granted. See [permissions](permissions.md).

**H5. Every request opened 20–30 SQLite connections and wrote to the
database.** `db.get_db()` opened a new connection (7 PRAGMAs each) per helper
call; `has_permission` hit the plugin table on every call; analytics did an
`INSERT … ON CONFLICT` with `synchronous=FULL` on every request
(`app.py:1514-1526`); `sync_with_registry` ran on every request
(`app.py:1318-1339`). Measured: 32 connections, 257 statements, 2 writes and
242 ms for one page view.
*Fixed.* One connection per request (`bananawiki/wiki/db.py`), permission
grants loaded once per request, the feature registry kept in memory, and
request counters buffered and written every few seconds
(`features/admin/analytics.py`).

**H6. A 500 MB request cap and unbounded body reads.** The global
`MAX_CONTENT_LENGTH` was the largest feature cap (`app.py:158-165`);
`/api/csp-report` read whole bodies before truncating (`app.py:1859-1890`);
drafts, preview and code highlighting accepted unbounded input
(`routes/api.py:335-409`).
*Partly.* The CSP report endpoint is gone; JSON bodies are refused above
2 MiB before parsing, form fields are limited to 2 MiB in memory, Markdown
input to 1,000,000 characters, and uploads stream to disk with per-kind
limits. The overall body cap is still the largest upload the configuration
allows (500 MiB for whole-site imports on self-hosted wikis), so a signed-in
user can still send a large file body that is spooled to disk before its
route refuses it; set a proxy body limit if that matters to you.

**H7. Attachments were stored twice and buffered in RAM.** Uploads went to
disk and into `file_blobs` (`routes/uploads.py:314-378`); downloads read the
whole blob (`:434-443`); "download all" built the ZIP in memory (`:458-492`).
*Fixed.* Files are stored on disk only and streamed; ZIPs are written to
temporary files. A 1.4 blob is still read when its file is missing, and
written back to disk (`bananawiki/wiki/storage.py`). Blob copies are removed
together with their attachment.

**H8. Search scanned every page's content in Python, without effective rate
limiting.** `_advanced_search_results` loaded all content
(`routes/wiki_search.py:135-281`, `db/_pages.py:249-262`); the rate limit
exempted browser navigation (`helpers/_rate_limiting.py:194-211`) and search
was public in public mode.
*Fixed.* A full-text index (`pages_fts`, FTS5) with visibility applied in SQL,
snippets built by SQLite, paging, and a per-user/address rate limit that
applies to HTML requests too.

### Medium

**M1. Restricted editors could rename, move and create any category.**
`routes/wiki_categories.py:81-185` checked only the permission; the cycle check
and update ran in separate connections (`db/_categories.py:31-53`).
*Fixed.* Every category action needs its permission **and** write access to
the categories involved; the cycle check and the move run in one transaction
(`features/pages/category_routes.py`, `categories.py`).

**M2. Any editor could delete any uploaded image by name**
(`routes/uploads.py:248-276`).
*Fixed.* `/api/upload/delete` is for administrators only and refuses images
that are still referenced unless forced.

**M3. The upload garbage collector raced with edits and scanned everything on
each save** (`routes/uploads.py:29-60`, called from every save).
*Fixed.* A background job (`pages.cleanup_uploads`, every 6 hours) removes an
image only when no text column anywhere mentions it and it is older than 24
hours.

**M4. Administrators could take over other administrators** by resetting
their password, demoting or suspending them
(`routes/admin_accounts.py:751-800, 969-986, 1033-1041`).
*Fixed.* Administrators are changed only by owners and superusers; owners
only by themselves; superusers only by themselves
(`features/admin/service.py`).

**M5. Stored HTML injection through `t(...)|safe`.** `t()` interpolated
unescaped values (`helpers/_translations.py:315-319`) into templates marked
`|safe` (`admin/chats.html:25`, `wiki/edit.html:46`,
`admin/user_permissions.html:8`, `admin/editor_access.html:8`,
`wiki/page.html:36`); portal-supplied usernames were not validated
(`routes/platform_oauth.py:364,721`); `str.format` allowed attribute
traversal in uploaded language packs.
*Fixed.* Translations are plain text, autoescaped in templates; placeholders
are replaced by a simple `{name}` substitution (no `str.format`); the rule
"no `|safe` on anything built from user input or translations with parameters"
is part of [ARCHITECTURE.md](../ARCHITECTURE.md). Platform sign-in creates
accounts through the normal sign-up rules.

**M6. The Markdown sanitiser allowed arbitrary `class` and `id`, and the
post-processing had bugs** (`helpers/_constants.py:19-27`,
`helpers/_markdown.py:39-58, 349-379, 744-749`): content could reuse the app's
CSS and JS hooks and clobber ids, `rel="opener"` survived, blank lines in code
blocks rendered as `&lt;br&gt;`, and six regex passes rewrote HTML after
sanitising.
*Fixed* (one part *open by design*). nh3 with a strict allow-list: known
classes only, `id` only on headings, limited `style`, forced
`rel="noopener noreferrer"`; embeds are generated from validated parameters
after sanitising (`bananawiki/wiki/markdown.py`). External `https:` images
are still allowed (`img-src https:`), so a page can still load an image that
reveals a reader's address to another site; this is documented in
[security](security.md#response-headers).

**M7. Renaming yourself silently rewrote pages you could not access**
(`db/_pages.py:671-699`: no history entry, different timestamp format); a
second dead implementation would also rewrite history and private chats
(`db/_users.py:264-345`).
*Changed.* Mentions are rewritten through the pages service
(`rewrite_mentions`): every changed page gets a history entry ("Updated
mention of @old", attributed to the system) and normal timestamps; drafts are
updated; history and chats are never rewritten.

**M8. `X-Forwarded-Host` and `X-Forwarded-Prefix` were trusted from clients**
(`app.py:180-182`; the generated nginx config did not set them,
`setup_wizard.py:487-504`).
*Fixed.* `X-Forwarded-Prefix` is never trusted; forwarded headers are only
read with `BW_PROXY_MODE=1`, and the shipped Caddy configurations strip
`X-Forwarded-Prefix` and set the others. The nginx example in
[deployment](deployment.md#reverse-proxy) overwrites all of them.

**M9. Background timers started at import time in the Gunicorn master and
duplicated per worker** (`routes/admin_sessions.py:530`,
`gunicorn.conf.py:109`, `app.py:1542-1712`).
*Fixed.* One scheduler (`bananawiki/wiki/registry.py`) started on the first
request of each worker (the app is not preloaded), with a lease per job in
`job_runs` so one worker runs each job; no timers at import time.
`bananawiki jobs run` can drive the jobs from cron instead.

**M10. The in-memory rate-limit store grew without bound, was per worker and
skipped GET navigation** (`helpers/_rate_limiting.py:126-211`).
*Partly.* The in-memory limiter caps its keys (20,000) and applies to every
method; sign-in and sign-up limits are in the database and shared by all
workers. The global and per-action limits remain per worker.

**M11. Data directories defaulted into the source tree** (`config.py:274-285,
339-404, 459-462`).
*Fixed.* Every folder defaults to the instance directory; on the first start
of 1.6 files found at the old defaults are moved there when the matching
variable is unset (`bananawiki/wiki/takeover.py`).

**M12. Last writer wins; multi-step writes were not atomic**
(`routes/wiki_editing.py:66-199, 298-304`).
*Fixed.* Pages carry a `revision`; saving an outdated copy shows a conflict
instead of overwriting, and the API accepts `expected_revision`. Every page
write goes through one service call in one transaction.

### Low

* **L1. Replayable bot protection, off in test mode** (`helpers/_bot_protection.py:84-151`).
  *Fixed:* single-use tokens (nonce recorded), honeypot, never switched off by
  configuration.
* **L2. "Remember me" off still gave a 7-day persistent cookie** (`routes/auth.py:299`).
  *Fixed:* without it the cookie ends with the browser session.
* **L3. `/admin/error-log` did its own session check** (`routes/errors.py:304-318`).
  *Fixed:* `admin_required` like every administrator page; secrets are masked
  in the log view.
* **L4. 404 and 403 differed for restricted pages**, revealing slugs
  (`routes/wiki_pages.py:80-87`, `routes/wiki_presence.py:33-38`).
  *Fixed:* anything the reader may not see answers 404.
* **L5. Maintenance mode cleared cookies without revoking sessions; `/api/v1`
  bypassed maintenance and forced steps** (`app.py:1372-1419`).
  *Fixed:* maintenance mode keeps sessions and blocks non-administrators; the
  API answers 503 and refuses accounts with pending forced steps.
* **L6. The storage-quota exemption matched substrings of endpoint names**
  (`app.py:1223-1225`). *Fixed:* the quota is checked where files are stored
  (`storage.save`).
* **L7. Undecryptable secrets were dropped silently; `SECRET_KEY` vs
  `BW_SECRET_KEY` confusion** (`helpers/_crypto.py:200-212`,
  `hosting/container_runtime.py:123`). *Partly:* both names are accepted
  (`SECRET_KEY` first); a value that no longer decrypts still reads as empty
  so the administrator re-enters it, and the federation page says when a
  pairing key cannot be read.
* **L8. Mixed timestamp formats compared as strings** (`db/_users.py:707`,
  `db/_pages.py:692`). *Fixed:* the 1.6 migration rewrites every timestamp to
  `YYYY-MM-DD HH:MM:SS` UTC and all code writes that shape.
* **L9. Deleting an attachment of a missing page crashed** (`routes/uploads.py:402-406`).
  *Fixed:* attachments are looked up through their page with its access check.
* **L10. Attachment defaults were documented wrongly** (`config.py`,
  `db/migrations/legacy.py:235`). *Changed:* the default is still "allow all"
  (downloads are always `application/octet-stream` unless harmless), and the
  documentation says so.
* **L11. The setup token was accepted in the URL; verbose logging of every
  page view by default** (`bootstrap.py:21`, `routes/auth.py:50`,
  `routes/wiki_pages.py:106`). *Fixed:* the token is only accepted in the
  posted form; the default log level is `medium`.
* **L12. `gunicorn.conf.py` used a private API and fixed sizing**
  (`:149-151`). *Fixed:* no private APIs; `BW_WORKERS`, `BW_THREADS`,
  `BW_WORKER_TIMEOUT`, `BW_ACCESS_LOG`.
* **L13. `MaintenanceGate` contradicted its docstring and stat'ed a file per
  request** (`banana_ops/gate.py:1-18`). *Changed:* the gate is documented as
  what it is (503 for everything except the health check while the updater's
  file exists).

## 2. Architecture and code quality

| 1.4 | 1.6 |
|---|---|
| `app.py` was a 1,924-line module with import-time side effects (database init, route registration, plugin loading, service start, `app.py:1897-1913`), a 600-line request guard chain (`:1160-1531`), inline HTML (`:1084-1116`) and hard-coded path matchers for ~20 "built-in plugins" (`:275-443`). | An application factory (`create_app()`), a documented request pipeline, one package per feature, and a registry that turns every feature on or off in one place. Nothing happens at import time. |
| Re-exports for the tests: ~50 private symbols in `app.py:40-80`, ~400 names in `db/__init__.py`; 210 `monkeypatch.setattr(config, …)` in tests. | A typed, immutable `Config` object; tests build apps with fixtures instead of patching modules. |
| Circular-import workarounds (`_lazy_routes_attr`, `importlib` inside hooks, function-local imports). | Features depend only on the shared services listed in ARCHITECTURE.md and talk to each other through events, slots and interceptors. |
| `config.py` created directories and keys and called `setrlimit` on import; ~117 environment variables, many read ad hoc. | `load_config()` reads and validates every variable once; invalid values stop the start with a clear message. |
| Two session systems plus a legacy flag, reconciled in three places. | One session table; see H2. |
| Three overlapping authorisation mechanisms; the tour mutated the user dict they all read. | One permission layer (`auth.has_permission`, category checks, object checks). |
| Function-per-query database module, a new connection per call, `retry_on_busy` everywhere, the whole pre-2026 schema in one 2,000-line migration step. | `db` session per request, explicit transactions (`BEGIN IMMEDIATE`, nested savepoints), versioned migrations. |
| Per-process mutable state that differed between workers (rate limiter, asset version, integrity-check time, plugin registry synced per request, timers, Fernet cache). | State that must agree across workers lives in the database (sessions, leases, sign-in limits); per-worker state is limited to caches and the global request limiter. |
| Dead code: `sync.py` (167 no-op calls), `db.update_username_mentions`, `db.generate_random_id`, `routes.register_all_routes`, `SYNC_*` constants, analytics skip-list of non-existent endpoints, the `/activation-*` pages, `restricted_suspension_session`, unreachable embed code. | Not carried over. |
| Copy-paste: the login template call repeated 7 times, duplicated safe-redirect and expiry helpers. | Shared helpers (`core/web.py` for redirects, `settings.public_mode_active()`). |

Kept on purpose, as the audit recommended: the refusal to create or replace a
missing database outside the serialized initialiser, atomic secret-key
creation with a permission check, DNS-pinned outbound requests, attachments
served as downloads, the nonce-based CSP, the dummy-hash timing check, and
the setup token.

## 3. Features and the plugin system

### Headline findings

1. **Chat, group and kanban attachment blobs were never deleted**, so
   retention and "clear chat" left the content in the database
   (`routes/chat.py:340`, `routes/groups.py:397`, `routes/kanban.py:1631,2110`).
   *Fixed.* No new blobs are written; removing an attachment, clearing a chat,
   retention, deleting a group, board, column or ticket removes files and any
   1.4 blob together, and the `chat.housekeeping`, `kanban.sweep_files` and
   `attachments.cleanup` jobs remove leftovers.
2. **Disabling the `attachments` plugin reset the upload policy to "allow all"**
   (also for kanban), and disabling any plugin wiped its settings
   (`routes/plugins.py:44-104`, `helpers/_validation.py:164-185`).
   *Fixed.* Switching a feature off never changes data or settings.
3. **"Disabled" did not stop background work**: temporary items and pending
   deletions were still purged (`app.py:1618-1621`, `db/_temporary.py:432-443`,
   `db/_deletion_slowdown.py:155-170`).
   *Fixed.* Jobs of a switched-off feature do not run; temporary schedules
   pause and pending deletions wait.
4. **Page and user hooks fired only on some code paths** (bulk delete,
   deletion purge, temporary expiry, federation fork, OAuth sign-up), leaking
   audio files and stale canvas nodes (`routes/bulk.py:165`,
   `db/_deletion_slowdown.py:161-166`, `routes/federation.py:187`,
   `routes/platform_oauth.py:721`).
   *Fixed.* Events are emitted by the services after commit, so every path
   (web, API, bulk, jobs, imports, federation, sign-up) fires them.
5. **The CSP silently broke features**: TTS word highlighting and leaderboard
   search had no nonce, `onclick="window.print()"` was blocked, the server
   restart form submitted without confirmation, custom-page YouTube embeds were
   outside `frame-src` (`wiki/page.html:53,60,216,224,231`,
   `leaderboard.html:197`, `admin/settings.html:1470`,
   `routes/custom_pages.py:934`).
   *Fixed.* No inline scripts or handlers; declarative hooks
   (`data-confirm`, `data-print`) in one script; `youtube-nocookie.com` is
   allowed in `frame-src`.
6. **Platform sign-in ignored the sign-up policy** and stored the access token
   in the signed (not encrypted) cookie (`routes/platform_oauth.py:193-198,
   382-387, 717-735`).
   *Fixed.* Accounts are linked by the portal's stable account id, new accounts
   follow the wiki's sign-up rules, tokens are used once and never stored,
   PKCE is used, and error details go to the log (`features/auth/platform_oauth.py`).
7. **The page builder was a second edit path with weaker checks**: with
   `page_builder_access=user` plain users could publish edits to any page they
   could read (`routes/page_builder.py:33-55`).
   *Fixed.* The builder needs the right to edit the page, honours protection,
   reservations and pending deletion, and publishes through the pages service.
8. **Reverting a kanban board destroyed tickets, comments, attachments and
   history** (`db/_kanban.py:1342-1461`).
   *Fixed.* Revert matches columns and tickets and restores fields and
   positions; nothing is deleted except new, empty columns.
9. **Polling recomputed everything**: chat re-rendered the whole history every
   2.5 s with a query per message and a write per poll; kanban synced every 3 s
   with a prune per GET and stored a full-board snapshot per drag, never
   pruned; the leaderboard diffed all history content on every view
   (`routes/chat.py:76-89, 217-235`, `db/_chats.py:82-100`,
   `routes/kanban.py:2188`, `db/_kanban.py:1252-1291`,
   `db/_leaderboard.py:209-258`).
   *Fixed.* Chats load the latest page and then only newer messages (one query
   for attachments, slower polling in hidden tabs); kanban clients apply
   incremental events, pruning is a job, snapshots are coalesced and capped at
   200 per board; leaderboard statistics are computed once per revision by a
   job and aggregated in SQL.
10. **Group moderation skipped the chat permission and feature checks**
    (`routes/groups.py:452-485, 509-556, 878-917`).
    *Fixed.* Every group route, moderation included, checks `chat.group` and
    `chat_group_enabled` (`features/chat/policy.py`).
11. **Dead token modules** `db/_api_tokens.py`, `db/_userbots.py` and their
    tables. *Fixed.* Not carried over; `bananawiki db prune-retired` drops
    the tables.
12. **Kanban and canvas shared one racy `list_order_version` counter**
    (`routes/canvas.py:487-488`, `routes/kanban.py:497-499`).
    *Fixed.* Each has its own order version derived from its own data.

### The plugin system

1.4 built-in "plugins" were mostly feature flags (15 of 19 had an empty
`on_load`), gated by at least six mechanisms (`app.py:293-443`, per-route
checks, `g.enabled_plugins`, scattered `is_plugin_enabled`,
`_PLUGIN_SETTINGS_TO_DISABLE`, the easy-wiki mask). Third-party plugins were
imported into the process with ~1,430 lines of hot enable/disable machinery
that could not really unload code (`plugin_loader.py:80-127, 436-741,
909-1040`), a tiny extension surface (7 hooks, 2 slots) and an SDK that
re-exported internals.

*Changed.* Built-in features are packages declaring a `Feature` with one
switch checked by routes, menus, jobs, events and permissions. Third-party
plugins remain possible (the audit suggested dropping them; they were kept for
compatibility) but use the same `Feature` API as built-in features, load only
at start-up, keep their tables under their own prefix enforced by SQLite's
authorizer, and 1.4 plugins run through an adapter. The upload checks,
password confirmation, database snapshot before enabling and
`BW_ALLOW_EXTERNAL_PLUGINS` stayed. See [plugins](plugins/README.md).

### Per feature

* **Chat**: deleted messages were only hidden and administrators still saw
  them (`db/_chats.py:354-365`) → *Changed:* deleting erases text and
  attachments for everyone. The "deleted" placeholder was translated at import
  time (`routes/chat.py:29`) → *Fixed:* translated per request. The upload code
  with joke audio conversion was copied three times → *Changed:* one storage
  service, joke audio dropped. A third scheduler (`routes/chat.py:639-716`) →
  *Fixed:* `chat.retention` job.
* **Groups**: `group_view` loaded every user with password hashes
  (`routes/groups.py:249`) → *Fixed:* member suggestions come from a search
  endpoint. One-character custom invite codes (`:899`) → *Fixed:* 6–32
  characters. System messages were English only → *Fixed:* translated.
  Owners and moderators can still add members directly, as in 1.4.
* **Kanban**: event sequence numbers could collide (`db/_kanban.py:1073-1116`)
  → *Fixed:* allocated under `BEGIN IMMEDIATE`. Open access let anyone
  overwrite the global board order with arbitrary ids (`routes/kanban.py:482-500`)
  → *Fixed:* only boards the user can see are reordered. N+1 queries per
  ticket → *Fixed.* Anonymous visitors could open public boards but not their
  tickets (`routes/kanban.py:83-92`) → *Fixed:* the read endpoints follow the
  same rule. 10,000-character titles → *Fixed:* boards 200, columns 100,
  tickets 300 characters. ~2,670 lines of inline JavaScript → *Fixed:* static
  modules.
* **Canvas**: any user with one share could view every public canvas and
  archived canvases were visible to signed-in users (`db/_canvas.py:370-438`)
  → *Fixed:* the kanban access model. Page renames rewrote canvas JSON
  without a version bump, so open editors overwrote them
  (`db/_canvas.py:492-525`) → *Fixed:* server changes go through the same
  versioned operations. Three sync paths and a MAX+1 race → *Changed:*
  operations plus a version check on whole-document saves. Inline JavaScript
  → *Fixed.*
* **Custom pages**: YouTube broken by the CSP → *Fixed.* Pages served from the
  404 handler could shadow future routes (`routes/custom_pages.py:99-105`) →
  *Fixed:* a catch-all rule that only matches when no route does, and paths
  whose first segment belongs to a route are refused.
* **Assessments**: a double submit could hit a unique constraint and answer
  500 (`db/_assessments.py:199-243`) → *Fixed:* handled. The answer key leaked
  on the points page when retakes were allowed
  (`account/assessment_points.html:26`) → *Fixed:* shown only to managers and
  to takers who cannot try again. Questions were raw JSON in a textarea →
  *Fixed:* a question editor.
* **Temporary items**: opening the admin page ran the deletions
  (`routes/temporary.py:41`) → *Fixed:* only the job does.
* **Read aloud**: highlighting dead under the CSP → *Fixed.* Speed-changed
  downloads ran ffmpeg in the request for every request
  (`routes/tts.py:555-567, 666-720`) → *Fixed:* each speed variant is encoded

  → *Fixed:* threaded server with a concurrency limit, `413` for long text,
  minimal unauthenticated `/health`. Extra per-worker thread pools → *Changed:*
  one worker (separate process or inline threads) claiming jobs from the
  database. The audit suggested dropping read aloud; it was kept and
  rewritten.
* **Page builder**: see headline 7.
* **Leaderboard**: date ranges counted a page's whole content as "added" for
  the first revision in the range (`db/_leaderboard.py:243-247`), counted
  pages the viewer could not see, and loaded one profile per entry → *Fixed*

* **Onboarding**: user creation duplicated the validation → *Fixed:* one

* **Users and profiles**: 24 hard-coded "fun" profile fields created by a

* **REST API**: banana mode duplicated maintenance mode → *Dropped.*

* **PDF export**: a second hand-written Markdown parser that dropped images

  as the page, with local images.
* **Obsidian sync** (`helpers/_obsidian_sync.py`, a server-side CLI asking
  for a password) → *Dropped;* use the REST API.

## 4. Database and schema

* **Dangling `-1` references.** 1.4 wrote `-1` ("system") into user columns
  with foreign keys switched off (`db/_pages.py::create_page`), so every
  later migration's foreign-key check would fail. *Fixed:* the 1.6 migration
  sets such references to NULL, or removes rows whose required parent is gone,
  before anything else.
* **Mixed timestamp formats** (`datetime('now')` and ISO with `+00:00` in the
  same columns, plus REAL epochs). *Fixed* for the wiki's TEXT timestamps (all
  rewritten to one shape); federation tables keep Unix seconds, as in 1.4.
* **Two category-ACL systems** (`editor_category_access` and
  `user_category_access`). *Fixed:* the old one is folded into the current
  one by the migration.
* **Plaintext secrets**: `telegram_sync_token` and the retired feedback bot
  settings, `federation_peers.secret`, the portal's
  `global_tts_gpu_auth_token`, `instances.admin_password_plain`. *Fixed:*
  retired secrets are erased, federation keys and the GPU token are
  encrypted, a 1.4 initial password still waiting to be shown is shown once
  and erased; new wikis never store one.
* **Missing indexes** on foreign keys used on hot paths and in cascades (97 in
  the wiki database) and no full-text index. *Partly:* the 28 that matter
  (attachments, chats, groups, badges, sessions, rate limits, kanban,
  federation, drafts, custom roles …) and an FTS5 index were added; the rest
  are on rarely used paths.
* **Dual-write `file_blobs`**. *Fixed:* no new blobs; see H7.
* **Three API-token tables and two retired-plugin table sets** created on
  every fresh install (`beta_testers`, `feedback_*`, …) and left over in old
  installs (`banana_ai__*`, `meetings__*`, `bw_oauth_provider__*`,
  `oauth_login__*`, `git_override__*`). *Changed:* left untouched by the
  upgrade (some hold personal data an operator may want to export first);
  `bananawiki db prune-retired` drops them after a backup.
* **Schema written outside the migration ledger** by the hosting portal
  (`hosting/instance_environment.py`, `hosting/instance_database.py`) and by a
  plugin's `on_load`. *Fixed:* tenants migrate their own databases; the
  profile field tables are part of the schema; plugins may only create
  `<plugin_id>__*` objects.
* **A 154-column `site_settings` row and a 50-column `users` table**, JSON
  and CSV in TEXT, booleans without CHECK. *Open, by design:* 1.6 keeps every
  1.4 table and column with the same meaning so an installation upgrades in
  place without rewriting data. Writes go through an allow-list with the
  bounds of the admin forms.
* **No way to take over a 1.4 database safely.** *Fixed:* the schema is
  versioned from the 1.4 baseline (application id `0x42574B49`, version 3);
  1.6 adds version 4, takes an automatic copy before migrating, refuses older
  (pre-ledger) and newer databases with an explanation.

## 5. Deployment, operations and the hosting platform

### Security

* **HIGH: the hosting service account was root-equivalent** (member of the
  `docker` group, `banana_ops/system.py:110-112,173-175`), and tenants ran as
  the same UID. *Partly:* the portal no longer has Docker access; a small
  root agent with a validated, narrow protocol runs containers
  (`bananawiki/ops/runtime_agent.py`, `RUNTIME_AGENT.md`). Tenants still share
  the service account's UID until archive operations move into the agent.
* **HIGH: `setup_wizard.py` was an unauthenticated, CSRF-able root web UI**
  writing systemd units from form input (`setup_wizard.py:42-43, 798-1315`).
  *Fixed:* removed.
* **`dev.sh` and `hosting/run.py` enabled the Werkzeug debugger on any
  address** (`dev.sh:17-18,139`, `hosting/run.py:24-28`). *Fixed:*
  `bananawiki serve --debug` refuses non-loopback addresses.
* **Tenant secrets on the `docker run` command line**
  (`hosting/container_runtime.py:180-181`). *Fixed:* a 0600 env-file in the
  agent's private directory.
* **The portal migrated untrusted tenant databases host-side with the
  portal's environment** (`hosting/instance_database.py:39-55,124-160`).
  *Fixed:* migrations run only inside the tenant container.
* **Tenant storage and log limits enforced inside the tenant**; logs never
  rotated (`container_runtime.py:143-147`). *Partly:* logs go to Docker's
  rotated log driver; the storage limit is still enforced by the wiki itself
  (use host quotas).
* **Portal `/health` returned exception text** (`hosting/app.py:390-399`).
  *Fixed.*
* **The in-portal subdomain proxy forwarded client headers and trusted
  `X-Forwarded-Proto`; `X-Forwarded-Prefix` trusted in both apps**
  (`hosting/_subdomain_proxy.py:881-914`). *Fixed:* the in-portal proxy is
  gone (the runtime publishes routes to the reverse proxy) and
  `X-Forwarded-Prefix` is not trusted.
* **The on-demand TLS `ask` endpoint was public** (`hosting/routes/domains.py:63-67`).
  *Fixed:* the Caddy configuration answers 404 for `/internal/*` on public
  listeners and calls it on loopback.
* **`legacy_redirect/manage.sh` ran as root with unvalidated input**. *Fixed:*
  replaced by a Caddy snippet (`deploy/Caddyfile.legacy-redirect`).
* **Setup token accepted in the URL**. *Fixed* (see L11).
* **Platform backups wrote a plaintext ZIP first; the key lived on the same
  host** (`hosting/backups.py:87,99`). *Partly:* the archive is streamed
  straight into the encrypted output, so no plaintext archive exists on disk
  (`bananawiki/hosting/runtime/platform_backup.py`); the backup key is still
  on the host (download it and keep it elsewhere).
* **The portal called five public IP-echo services at start**
  (`hosting/config.py:442-530`). *Fixed:* the outbound interface address is
  used; nothing is sent.
* **The hosting admin CLI took passwords on the command line and wrote its
  audit log into the read-only release** (`hosting/admin_cli.py:124-145`).
  *Changed:* the CLI is gone; the portal's administrator pages cover its
  functions, and the wiki's `bananawiki` command reads passwords from a
  prompt, a file or standard input.

### Reliability

* **All tenant traffic went through a synchronous Python proxy with 8 slots**
  (`hosting/gunicorn.conf.py:56,67`, `hosting/_subdomain_proxy.py:821-1030`).
  *Fixed:* the in-portal proxy is gone; the runtime agent writes one Caddy
  site block per running wiki (`proxy.routes` in `RUNTIME_AGENT.md`), so wiki
  traffic goes straight from Caddy to each container.
* **Tenant starts ran inside request handlers for minutes** (a test took
  255 s). *Changed:* the runtime interface requires lifecycle calls to return
  once Docker confirms the action (about a minute at most); readiness is
  reported later by status calls.
* **Update downtime grew with the data size**: the full package was written
  after services stopped (`manager.py:381-383`). *Fixed:* an online snapshot
  (SQLite backup API, hard links for uploads) is taken first; downtime covers
  only what changed; the package is written after the site is back.
* **Disk leaks**: `before-update-*` packages and tenant images never pruned,
  tenant logs never rotated. *Fixed:* packages and releases are pruned to the
  retention count, old images removed, Docker rotates tenant logs.
* **Non-reproducible releases**: version ranges resolved at every update, 400 MB
  of downloads, unpinned base images. *Partly:* installs use wheels only (no
  build scripts on the server) and Dependabot proposes updates, but ranges
  are still resolved at install time and the base image is pinned by tag,
  not digest.
* **Stale default tenant image tag `1.4.4`** (`hosting/config.py:615-617`).
  *Fixed:* `bananawiki-tenant:latest` by default; managed servers set the
  deployed commit.
* **A background `compileall` of the read-only release at portal start**
  (`hosting/app.py:279-296`). *Fixed:* bytecode is compiled when images are
  built; nothing is written to the release.
* **Two drifting Caddy configurations**. *Fixed:* one renderer produces both
  the installed file and the shipped examples (tests compare them).
* **Leftovers of retired deploy scripts** (`helpers/_server_restart.py:235-330`,
  `.dockerignore`). *Fixed:* not carried over.
* **MFA keys derived from `HOSTING_SECRET_KEY`**. *Open, by design:* kept
  byte-compatible so enrolled authenticators keep working; documented.
* **Debug prints in the desktop app's start path**
  (`easy_deployment_app/main.py:742-748`). *Fixed:* the launcher was
  rewritten.

### The updater contract

The first 1.6 release is deployed by the 1.4 updater, so it keeps every
requirement the audit listed (C1–C14): a fast-forward commit, `banana` and
`LICENSE` at the root, `requirements.txt` installable into a plain venv,
`Dockerfile.tenant`, the entry points `gunicorn.conf.py`/`wsgi:app`,
`scripts/tts_worker.py`, `hosting.wsgi:app` and `hosting.maintenance`, a
read-only release tree, the existing environment names, `/health` answering
during maintenance, `hosting.db` and tenant directory names and container
labels, the schema baselines, the data layout and the `config/*.json` files.
The BananaChat hash-manifest coupling (C14) was removed: the controller is
BananaWiki's own. After the first update the 1.6 controller takes over and
converges the units (see [UPGRADING](../UPGRADING.md)).

### Packaging

* No `pyproject.toml`, no version, no tags, 18 top-level modules. *Fixed:*
  one `bananawiki` package with `pyproject.toml` and `__version__`; the root
  keeps only the entry points the updater needs.
* `piper-tts` (~160 MB) and the Google API client (~103 MB) installed for every
  wiki. *Partly:* they are optional extras in `pyproject.toml` (`tts`,
  `hosting`); `requirements.txt`, which the 1.4 updater and the images use,
  still includes them.
* No plain-wiki image or compose file. *Fixed:* `Dockerfile`, `compose.yaml`.
* `bleach` deprecated. *Fixed:* nh3.

### CI and tests

* No image builds, no upgrade test, no dependency audit, no secret scanning,
  no shellcheck, minimal lint rules. *Partly:* CI builds both images and
  starts them read-only under an arbitrary UID, runs `pip-audit`, ShellCheck
  and a wider ruff rule set, and tests Python 3.11–3.13; a regression test
  (`tests/test_upgrade_from_1x.py`) boots 1.6 on a real 1.4 instance and
  checks that accounts, sessions, API tokens, content and files survive. There is no end-to-end `banana install` →
  `update` → `rollback` test on a real systemd host.
* 4,925 tests in one flat directory named after releases and bugs, with
  process-spawning hosting tests (one took 255 s) and tests that failed without
  `ssh-keygen`. *Changed:* a new suite organised by module with a fake
  hosting runtime.

## 7. What remains open

In one place, the limitations stated above:

* The global request body cap equals the largest configured upload (H6).
* External `https:` images in pages can reveal readers' addresses (M6).
* Global and per-action request limits are per worker (M10).
* Tenant containers share the service account's UID; tenant storage limits
  are enforced inside the tenant; the platform backup key lives on the host.
* `site_settings` and `users` stay wide tables for in-place compatibility.
* `requirements.txt` still installs Piper and the Google API client.
* No end-to-end upgrade test on a real systemd host.
